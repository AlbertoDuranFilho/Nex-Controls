# Fase 8 — App Android Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Refazer o app Expo em `mobile/` sobre o Supabase: catálogo com preço do cliente, carrinho, pedido, pedidos e conta, tudo dentro do app.

**Architecture:** O app usa `@supabase/supabase-js` (sessão em `expo-secure-store`) e chama as mesmas tabelas/RPCs que o site (`precos_cliente`, `carrinho_adicionar`, `simular_pedido`, `criar_pedido`, etc., sob RLS). Única peça nova no site: rota `POST /api/app/pedidos/[id]/notificar` (Bearer do usuário) que dispara `notificarPedido`.

**Tech Stack:** Expo (SDK estável mais recente) + expo-router, TypeScript, supabase-js, lucide-react-native, jest-expo + @testing-library/react-native; no site Next.js 15 + Vitest + Playwright.

**Spec:** `docs/superpowers/specs/2026-11-26-fase8-app-design.md`

## Global Constraints
- Ler o site como referência de regra de negócio: `web/services/{catalogo,carrinho,pedidos}.ts`, `web/lib/carrinho/*`, `web/components/catalogo/*`, migrations em `supabase/migrations/`. Mesmas mensagens de bloqueio do carrinho (`web/lib/carrinho/mensagens.ts`) em português.
- App só em português nesta fase (textos centralizados em `mobile/constants/textos.ts`).
- Paleta preta/branca/cinzas em `mobile/constants/tema.ts` (preto `#0A0A0A`, branco, cinzas). Cantos: cartões 12–16, botões/campos 12, selos pill. Etiqueta de código preta com texto branco.
- Cartão de produto mantém o layout de `mobile/components/ProductCard.tsx` (horizontal, imagem 80×80 à esquerda) acrescentando preço/estado e botão de adicionar.
- Nunca usar a service role no app. Só `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (ou anon) e `EXPO_PUBLIC_SITE_URL` em `mobile/.env.example`.
- Acessibilidade: `accessibilityLabel`/`accessibilityRole` em botões só-ícone; alvos ≥ 44 pt.
- Remover código do Strapi (axios, `services/api.ts`, tipos Strapi, telas "Novidades/subscribe", assets react-logo).
- `app.json`: nome "Nex Controls", slug `nex-controls`, `android.package` `br.com.nexcontrols.app`, scheme `nexcontrols`, ícone/splash a partir de `assets/images/logo.png` (fundo branco), `userInterfaceStyle: "light"`.
- Testes do app: `cd mobile && npx tsc --noEmit && npx expo lint && npx jest`. Do site: `cd web && npx tsc --noEmit && npm run lint && npx vitest run && CI=true npx playwright test`. Lockfile do web só com `npx -y npm@10 install --package-lock-only --ignore-scripts`.

## Review Focus
- Visitante nunca vê preço nem botão de carrinho; lojista inativo ou produto sem preço → "Sob consulta".
- Sessão expirada: o app renova ou volta ao login sem travar.
- Rota de notificar: recusa sem token, token de outro cliente, pedido já notificado (idempotente) — não envia e-mail duas vezes.
- Gerar pedido com cupom inválido/mínimo não atingido mostra a mesma mensagem do site.
- Lista vazia, sem imagem, nome longo não quebram o cartão.

### Task 1: Rota do site para notificar pedido do app

**Files:** Create `web/src/app/api/app/pedidos/[id]/notificar/route.ts`, teste Vitest ao lado de onde os testes do web ficam, e2e/API test em `web/e2e/`; Modify `web/README.md` (seção app).

- [ ] `POST` lê `Authorization: Bearer <access_token>`; valida com `createAdminClient().auth.getUser(token)`; busca o pedido pelo id com service role; 401 sem/inválido token, 404 se o pedido não existe ou não é do lojista do usuário (`pedidos.lojista_id` = id do usuário — confirme a coluna), 200 `{ jaNotificado: true }` se `notificado_em` já preenchido, senão chama `notificarPedido(id)` e responde 200 `{ enviado: boolean }`. Sem CORS (app nativo).
- [ ] Testes: sem token 401; token de outro lojista 404; já notificado não chama `notificarPedido`; caminho feliz chama uma vez. Tudo verde. Commit.

### Task 4: Carrinho, pedido, pedidos e conta

**Files:** `mobile/app/(abas)/{carrinho,pedidos,conta}.tsx`, `mobile/app/pedido/[numero].tsx`, `mobile/lib/pedidos.ts`, componentes, testes.

- [ ] Carrinho: itens em cartões com miniatura, stepper, remover; cupom; resumo via `simular_pedido`; bloqueios com as mensagens do site; aviso sem endereço; "Gerar pedido" → `criar_pedido` → chama a rota de notificar em segundo plano (falha silenciosa) → tela de sucesso com o número → limpa contador.
- [ ] Pedidos: lista em cartões com selo de status colorido (mesmos tons do site); detalhe com itens, totais, linha do tempo e "Ver nota fiscal" (DANFE `https` com `expo-web-browser`).
- [ ] Conta: dados e endereço (leitura), "Fale conosco" (WhatsApp/e-mail), política de privacidade, "Excluir minha conta" (abre e-mail/WhatsApp com pedido de exclusão), "Sair".
- [ ] Testes: mensagens de bloqueio, mapeamento de status, fluxo de gerar pedido chama notificar após sucesso e não chama após erro. README do mobile com como rodar (Expo Go/dev build) e gerar o `.aab` com EAS. Commit.
